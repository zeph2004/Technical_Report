\chapter{Problem Analysis and System Requirements}
\label{ch:requirements}

\section{Existing Problem or Process}
Before we started working on a unified solution, users had to manually inspect their text messages or rely on simple mobile-based filters. If an SMS seemed suspicious, there was no easy way for a user to check its validity. Furthermore, administrators had no centralized way to collect scam patterns, view fraud trends, or block suspicious numbers. This made mobile-money fraud a highly profitable and low-risk crime for scammers.

\section{Problem Analysis}
Through my research, I identified several root causes for this problem:
\begin{itemize}
  \item \textbf{High Volume and Urgency:} Users receive many transactional messages daily. Scammers create a sense of extreme urgency (e.g., "Account blocked, click here immediately"), which tricks users into making hasty decisions.
  \item \textbf{Disconnected Systems:} Mobile platforms, backend APIs, and machine learning models are usually built as separate systems. If they do not communicate using clear, unified contracts, messages are not scanned consistently.
  \item \textbf{Rule Limitations:} Simple rule engines can only catch exact word matches. They cannot detect semantic context, which is where machine learning is needed.
\end{itemize}

\section{Proposed Solution}
To address these challenges, I worked on the Argus system, which joins a local rule engine and a server-side AI model:
\begin{itemize}
  \item The \textbf{Flutter Mobile App} provides the immediate frontend experience, listening for incoming SMS messages on Android and running quick keyword tests.
  \item The \textbf{Spring Boot Backend} manages secure connections, orchestrates user operations, and communicates with the ML model.
  \item The \textbf{FastAPI ML Service} acts as the intelligence layer, loading a BERT classifier to perform deep contextual text classification.
  \item The \textbf{React Web Portal} acts as the administrative control center where security officers can view stats, manage blocked senders, and monitor alerts.
\end{itemize}

\section{System Users and Actors}
The main users and actors in the Argus platform are:
\begin{itemize}
  \item \textbf{Mobile User:} The end-user who receives SMS alerts on their phone, manually scans messages, reviews local history, and provides feedback on whether a scan was accurate.
  \textbf{System Administrator:} The security officer who logs into the React web dashboard to see fraud analytics, manage spam sender numbers, and view alerts.
  \item \textbf{Flutter Client:} The mobile application that interacts with Android SMS receivers, local storage, and backend APIs.
  \item \textbf{React Client:} The web application used by administrators to communicate with the Spring backend.
  \item \textbf{Spring Boot Backend:} The core orchestrator that handles user authentication, database operations, and calls the machine learning service.
  \item \textbf{FastAPI ML Service:} The service that accepts text inputs and predicts whether they are fraudulent.
\end{itemize}

\section{System Constraints}
Several constraints influenced the design and implementation of this system:
\begin{itemize}
  \item \textbf{Platform Limitation:} Automatic SMS interception is only possible on Android devices due to iOS security restrictions.
  \item \textbf{Database Dependency:} The backend API requires a running PostgreSQL database to persist user credentials and scan records.
  \item \textbf{Computational Resources:} A BERT NLP model is too heavy to run directly on a typical mobile device, requiring a server-side API for inference.
  \item \textbf{Authentication Differences:} The mobile client, web client, and backend currently have different endpoint expectations that must be aligned.
\end{itemize}

\section{Assumptions}
In designing the requirements, I made the following assumptions:
\begin{itemize}
  \item Users will grant the necessary Android permissions for reading and receiving SMS messages.
  \item The mobile device will have internet connectivity when a server-side scan is requested.
  \item Scanned messages are non-empty and written in English or Swahili (the primary languages supported by our keyword rules and BERT training context).
\end{itemize}

\section{Data Requirements}
The data exchanged across the system must follow strict contracts:
\begin{itemize}
  \item The ML service requires a JSON request containing a \texttt{message} string, and returns a JSON response with \texttt{message}, \texttt{label}, \texttt{is\_scam}, and \texttt{confidence}.
  \item PostgreSQL scan records must store the sender's number, message body, scan source (manual or auto-ingestion), confidence rating, and timestamp.
\end{itemize}

\section{Security and Privacy Requirements}
SMS content can contain highly private information, such as passwords, personal chats, or financial details. Therefore, the system must protect this data. No plain text passwords should be stored; they must be hashed using BCrypt. JWTs must be used to protect all backend routes, and the mobile app should store its credentials securely using local \texttt{SharedPreferences}.

\section{Workflows and Use Cases}
Instead of relying on complex diagrams, I mapped out the system's workflows using two main use cases:

\subsection{Mobile User Scan Workflow}
\begin{enumerate}
  \item An SMS arrives on the user's Android phone.
  \item The background service intercepts the message.
  \item The app immediately runs the local heuristic scan to show an offline warning if needed.
  \item If internet is available, the app calls the Spring Boot API, which queries the FastAPI BERT service.
  \item The mobile dashboard updates, showing the AI model's prediction and saving the message to the local log.
\end{enumerate}

\subsection{Administrator Portal Workflow}
\begin{enumerate}
  \item The security officer logs into the Admin Web Portal using their email and password.
  \item The React client requests statistics from the Spring Boot admin endpoints.
  \item The dashboard renders real-time charts showing the number of scanned messages, threat trends, and registered users.
  \item The admin can view specific scans marked as scams and add problematic senders to the blocked list.
\end{enumerate}
